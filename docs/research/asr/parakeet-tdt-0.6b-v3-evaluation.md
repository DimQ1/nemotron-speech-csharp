# Оценка: nvidia/parakeet-tdt-0.6b-v3 для ASR-стриминга

**Дата:** 2026-08-26
**Ветка:** `feature/parakeet-tdt-0.6b-v3-eval`
**Кандидат:** [nvidia/parakeet-tdt-0.6b-v3](https://huggingface.co/nvidia/parakeet-tdt-0.6b-v3)
**Текущая модель проекта:** [nvidia/nemotron-3.5-asr-streaming-multilingual-0.6B](https://huggingface.co/nvidia/nemotron-3.5-asr-streaming-multilingual-0.6B) (FastConformer-CacheAware-RNNT, 600M)

---

## Краткий вывод

- **Качество:** выше, чем у текущей RNN-T модели, за счёт TDT-декодера и более свежего обучения (Granary + NeMo ASR Set 3.0). На Open ASR Leaderboard средний WER **6.32 %**; английский **4.85 %**, русский **5.51 %**, украинский **6.79 %**.
- **Стриминг:** поддерживается. TDT (Token-and-Duration Transducer) изначально спроектирован для потокового распознавания — предсказывает одновременно токен и его длительность, что даёт точные временные метки и стабильный chunked-вывод.
- **Главный риск для этого проекта:** интеграция в C#-стек на ONNX Runtime GenAI. TDT — нестандартный декодер, его конвертация NeMo → ONNX (GenAI) требует проверки; альтернативы — NeMo-Speech.cpp (GGUF) или Transformers (Python).

## 1. Описание модели

| Параметр | Значение |
|---|---|
| Архитектура | FastConformer-TDT (энкодер FastConformer + декодер TDT) |
| Параметры | 600M |
| Языки | 25 европейских (вкл. **русский**, **украинский**), автодетект языка |
| Вход | 16 kHz, моно, `.wav`/`.flac` |
| Выход | Текст с пунктуацией и капитализацией |
| Таймстампы | word-level и segment-level (точные, из TDT durations) |
| Длинное аудио | до 24 мин (full attention на A100 80GB), до 3 ч (local attention) |
| Лицензия | CC BY 4.0 (коммерческое использование разрешено) |
| Рантаймы | NeMo (PyTorch), NeMo-Speech.cpp (GGUF), Transformers |
| Дата релиза | 14.08.2025 |

**Что такое TDT.** TDT-декодер (paper [arxiv:2304.06795](https://arxiv.org/abs/2304.06795)) — гибрид CTC и RNN-T. На каждом шаге предсказывает пару `(token, duration)`, поэтому:
- длина вывода привязана к длительности кадра, а не к числу бланк-символов;
- временные метки получаются напрямую без пост-обработки;
- стриминговый вывод стабильнее, чем у классического RNN-T.

## 3. Стриминг-возможности

**Да, стриминг поддерживается нативно.** В NeMo используется chunked-инференс:

```bash
python speech_to_text_streaming_infer_rnnt.py \
    pretrained_name="nvidia/parakeet-tdt-0.6b-v3" \
    right_context_secs=2.0 \
    chunk_secs=2 \
    left_context_secs=10.0 \
    batch_size=32
```

- `chunk_secs` — размер стримингового чанка.
- `left_context_secs` / `right_context_secs` — контекст внимания вокруг чанка.
- TDT выдаёт временные метки и в потоковом режиме (`timestamps=True` → char/word/segment).

**Следствие для проекта:** модель принципиально подходит для `IStreamingSpeechRecognizer` (тот же контракт, что использует текущий Nemotron-провайдер в `SpeechLib.Nemotron`).

## 6. Статус конвертации и интеграции (2026-08-26)

**Конвертация и интеграция решены** — TDT-модель работает через обычный
ONNX Runtime (не GenAI):

- Готовые артефакты: `istupakov/parakeet-tdt-0.6b-v3-onnx` / `PalatineVision/...`
  (`encoder-model.onnx` + `decoder_joint-model.onnx` + `nemo128.onnx` +
  `vocab.txt` + `config.json`; FP32 и INT8). Способ конвертации — NeMo
  `model.export()`, референс-декодер — пакет `onnx-asr` (MIT, istupakov).
- Точность: WER 2.16 % LibriSpeech test-clean (INT8 = FP32), RTF ~0.05 (~20× real-time).
- Реализован C#-провайдер `SpeechLib.ParakeetTdt` (`IStreamingSpeechRecognizer`
  поверх `Microsoft.ML.OnnxRuntime`) — собирается без ошибок, greedy-логика
  верифицирована на `Test-Audio/librispeech` (корректный транскрипт).
- **Стриминг** — buffer-based (перекрывающиеся окна `left|chunk|right` через
  полный encoder, TDT-состояние переносится между чанками). Cache-aware
  `forward_for_export` неприменим: у модели `att_context_style="regular"`
  (full attention) — подтверждено инспекцией NeMo 3.0 `ConformerEncoder`.
- Модель выложена на HF: `DimQ1/parakeet-tdt-0.6b-v3-onnx` (папки
  `fp32/`, `int8/`, `int4/`).
- Сервер-обёртка (альтернатива): `groxaxo/parakeet-tdt-0.6b-v3-fastapi-openai`.

Ограничение: ORT GenAI (текущий Nemotron-стек) TDT не поддерживает — провайдер
использует обычный OnnxRuntime и buffer-based стриминг.

## 7. Настоящий стриминг (2026-09-28)

### Что было

Буферный стриминг с чанком 2 с и правым контекстом 2 с: слово попадало в
транскрипт через 2–4 с после произнесения, промежуточного текста не было.
Замер на `Test-Audio/cv17/en` (250 клипов, fp32, CPU 20 ядер): WER 10.30 %,
RTF 0.077, первый текст в среднем через 4.0 с аудио (offline: WER 9.99 %).

### Что можно сделать с offline-моделью

Cache-aware стриминг требует модели, обученной с ограниченным контекстом
(`att_context_style=chunked_limited`); у parakeet-tdt-0.6b-v3 контекст
`regular`, экспорт с кэшем невозможен. Остаётся буферный подход, но его можно
сделать по-настоящему потоковым: каждые `chunk` секунд один проход энкодера по
окну `[левый контекст | незакоммиченное аудио]`, и два прохода TDT-декодера
с копии состояния:

1. кадры, у которых уже есть `rightContext` будущего аудио → **коммит**
   (токены финальные, состояние декодера продвигается);
2. оставшийся хвост → **превью** (ревизуемый частичный текст, состояние
   отбрасывается).

Текст появляется через ≤ `chunk` после произнесения, фиксируется через
`rightContext` — сопоставимо с cache-aware Nemotron (чанк 560 мс).

### Что выяснилось при отладке (важно для любой модели с TDT-декодером)

- **Жадный TDT теряет целые фразы после паузы.** После точки состояние
  prediction-сети смещено к blank; в тишине модель предсказывает
  «blank, пропустить 4 кадра», начало следующей фразы попадает внутрь
  пропуска, и декодер молчит до следующего сильного начала. Это свойство
  модели, а не стриминга: offline-декод 16 склеенных клипов Common Voice с
  паузами 0.7 с дал WER **47.5 %** (потеряно 6 фраз из 16).
- Началу фразы после паузы нужно 2–4 с правого контекста, чтобы joint предпочёл
  первый токен blank'у; словам внутри фразы хватает ~1 с. Поэтому граница
  коммита двигается только за последний распознанный токен; кадры без токенов
  остаются «открытыми» и передекодируются с растущим контекстом, пока не
  станут старше `silenceContext` (2 с).
- Перенос «перелёта» длительности TDT через границу шага вреден — повторный
  декод первого кадра шага даёт модели второй шанс на начало фразы, а повтор
  кадра после уже выданного токена даёт blank (дублей нет).
- **Сброс состояния декодера после паузы ≥ 0.8 с** (как в NeMo при
  посегментном декодировании) убирает смещение к blank. Аудио-контекст
  энкодера при этом сохраняется. На той же 99-секундной записи стриминг даёт
  WER **18.0 %** против 47.5 % offline и 60.4 % у старой геометрии 2/2.
- Ровно нулевая цифровая тишина (склейка нулями, пустой loopback) выбивает
  нормализацию mel-признаков (NeMo обучает с dither 1e-5); фикстуры для
  проверки пауз нужно склеивать «комнатным шумом», а не нулями.

### Реализация

`libraries/SpeechLib/src/SpeechLib.Providers/ParakeetTdtRecognizer.cs`:

- `Step` — один проход энкодера по окну `[5 с левого контекста | открытая
  область]` каждые 0.32 с нового аудио; фаза 1 (кадры с полным правым
  контекстом) → коммит, фаза 2 (хвост) → превью с копии состояния.
- Правый контекст: 1 с для слов внутри фразы, **2 с для первого слова фразы**
  (свежее состояние декодера); из окна короче 3.84 с ничего не коммитится
  (в начале сессии нет левого контекста, а энкодер нормализует признаки по
  окну) — превью при этом показывается сразу.
- Граница коммита двигается только за последний токен; тишина остаётся
  открытой до `silenceContext` = 2 с.
- `HasTrailingSilence` — конец фразы по blank-кадрам с полным контекстом
  **или** по энергии (аудио после последнего токена ниже порога тишины ≥ 0.8 с);
  «пустое превью» доказательством не считается (хвост без правого контекста
  смещён к blank и рвал фразы посередине).
- `StartNewUtteranceState` — свежее состояние после паузы.
- Энергетический гейт: если открытая область тише 1 % от максимального пика
  сессии (не выше −54 dBFS) и превью пусто, шаг учитывается как blank без
  энкодера — в паузах нагрузка падает до нуля; порог относительный, чтобы
  тихие записи (в Common Voice есть клипы с пиком −55 dBFS) не терялись.
- Адаптивный шаг: следующий шаг не раньше, чем 1.25 × время вычисления
  предыдущего — на слабом CPU растёт шаг, а не очередь.
- Абсолютные позиции сэмплов переживают обрезку буфера (раньше endpointing
  сбивался после каждой обрезки).

Параметры (`chunk`, `right`, `left`, `silence`, `onset`, `preview`) доступны через
`RecognizerFactoryOptions.Streaming*`; CLI `NemotronSpeech` принимает папку
Parakeet напрямую. Диагностика: `SPEECHLIB_PARAKEET_TRACE=1` печатает
арифметику окна и решения декодера по кадрам. Харнесс `tools/WerEval
--streaming` получил `--chunk/--right/--left/--silence/--onset/--no-preview`,
метрики «preview WER» (текст на экране перед flush против финального) и
«первый текст» (секунды аудио до первого превью / первого коммита).

### Замеры (fp32, CPU, 20 логических ядер)

Дефолты: шаг 0.32 с, правый контекст 1 с (2 с для первого слова фразы), левый 5 с,
тишина 2 с, превью включено. «Первый текст» — секунды аудио до первого превью /
первого коммита (клипы Common Voice начинаются с ~0.5–1 с тишины).

| Набор | Offline | Старый стриминг (2 с / 2 с) | Новый стриминг | RTF нов. | Preview WER | Первый текст |
|---|---:|---:|---:|---:|---:|---:|
| cv17/en, 250 клипов | 9.99 % | 10.30 % (RTF 0.077, текст через 4.0 с) | 11.05 % | 0.41 | 0.54 % | 1.6 / 4.2 с |
| cv17/ru, 250 клипов | 5.75 % | — | 6.14 % | 0.36 | 0.24 % | 1.2 / 4.1 с |
| TTS, один голос, 14 фраз, 58 с | 5.41 % | — | 6.31 % | 0.45 | 0.00 % | 0.8 / 4.2 с |
| 16 клипов CV разных дикторов, 99 с | 47.5 % | 60.4 % | 20.1 % | 0.52 | 0.00 % | 0.8 / 4.0 с |
| 3 клипа CV, 16.5 с | 36.8 % | 31.6 % | 15.8 % | 0.49 | 0.00 % | 0.8 / 4.0 с |

Для сравнения Nemotron 3.5 ASR streaming fp32 (каталог моделей): cv17 en 20.55 %,
ru 12.52 %, всего 16.71 %.

Выводы: на одиночных фразах новый стриминг близок к старому и к offline, при
этом текст появляется через ≤ 0.32 с + время шага (на этой машине ≈ 0.45 с);
на многофразных записях стриминг заметно точнее offline-декода (свежее состояние
после паузы). Цена — CPU: RTF ≈ 0.35–0.5 на 20 ядрах (энкодер по окну 6–7 с
трижды в секунду); на слабом CPU шаг растёт автоматически. Склейка разных
дикторов остаётся стресс-тестом: часть начал фраз после смены голоса модель не
берёт ни в одном режиме.
